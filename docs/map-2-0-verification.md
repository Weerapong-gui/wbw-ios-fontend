## ข้อจำกัดที่เจอระหว่างทาง

1. **ความเสี่ยงเรื่อง `timeSamples` ไม่แปลงเป็นแอนิเมชันไม่เกิดขึ้นจริง** — สเปก §8 เปิดความเสี่ยงไว้ว่า
   RealityKit อาจไม่แปลง `timeSamples` ของ Blender ให้เป็น `availableAnimations` เล่นได้ ของจริง
   (Task 6) คือแปลงได้ครบ เมฆขยับจริงตั้งแต่ครั้งแรกที่สั่ง `playAnimation` ไม่ต้องเขียนแอนิเมชันเอง
   แทนตามที่สเปกเตรียมทางหนีไว้

2. **`-uitestMapPin N` ตั้งได้แค่สถานะการ์ด ไม่ขยับกล้อง** — launch flag นี้ (Task 2) เรียกแค่
   `tappedSequence` ไม่เคยเรียก `focus(on:at:)` เลย เพราะโค้ดจุดนี้ไม่ได้อยู่ในไฟล์ที่แผนสั่งแตะ
   ผลคือการยืนยัน "กล้องบินไปหมุด" ต้องจำลองการแตะจริงบนจอ (`cliclick` เทียบพิกัดสกรีนช็อต)
   แทนการพึ่ง launch flag เพียงอย่างเดียว — ทุก task ถัดมาที่ต้องดูกล้องบินต้องรู้ข้อจำกัดนี้ล่วงหน้า

3. **launch flag ที่ไม่มีค่าต่อท้ายไม่ทำงาน** — `-uitestDemo` เฉย ๆ ไม่ตั้ง `UserDefaults` ให้ ต้องเป็น
   `-uitestDemo 1` เสมอ เจอปัญหานี้ซ้ำในหลาย task (Task 1 รอบแก้, Task 4, Task 5, Task 6) เพราะ
   launch flag ทั้งหมดอ่านผ่าน `UserDefaults.standard.bool(forKey:)`/`string(forKey:)` ซึ่งต้องการคู่
   `-key value` ที่สมบูรณ์ — flag เดี่ยวไม่พังตอน build/run แค่เงียบ ๆ ไม่เข้าเงื่อนไขที่ตั้งใจ

4. **เทส 3 คลาสเดิมยัง flaky ตลอดทั้งแผน จำนวนแกว่งไปมา 0-47 โดยไม่มีการแก้ซอร์สที่เกี่ยวข้อง** —
   `ChatSessionPersistenceTests`, `FeedbackTransportTests`, `GroupLeaveTransportTests` ใช้
   fake `URLProtocol` แบบ process-wide ร่วมกันเป็น shared state จึงแข่งกันเองตามลำดับรัน
   ตัวเลข failure ที่รายงานไว้ตลอดแผน: Task 1 = 24, Task 2 = 21 และ 42 (สองรอบ), Task 3 = 0,
   Task 4 = 41, Task 5 = 47, Task 6 = 44/17/0 (หลายรอบ), รอบนี้ (Task 7) = 47 (นับ assertion)
   / 17 เคสจริง — **`Map3D*`/`MapModelLoaderTests` ผ่าน 0 failure ทุกรอบตลอดทั้งแผน ไม่เคยมีข้อยกเว้น**

5. **มีแค่ 1 task (ไม่ใช่ 2) ที่ต้องแตะไฟล์เทสนอกรายชื่อไฟล์ของแผน** — Task 4 ต้องแก้
   `WBWTests/TrailRouteTests.swift` เพิ่ม (`testBundledRouteStaysInsideEventArea()` เรียก
   `Map3DGeo.eventArea` ตรง ๆ) ทั้งที่ไฟล์นี้ไม่ได้อยู่ในรายชื่อไฟล์ของ Task 4 เพราะตอนวางแผน grep
   ผู้เรียก `Map3DGeo.eventArea` ครอบคลุมแค่โค้ดใน `WBW/` ไม่ได้ครอบคลุม `WBWTests/` ด้วย —
   ตรวจรายงาน Task 1, 2, 3, 5, 6 แล้วไม่มี task อื่นเจอกรณีเดียวกันอีก (บันทึกไว้ที่นี่เพราะร่างเอกสารนี้
   เข้าใจผิดไว้ก่อนว่ามี 2 task ที่เจอ — ตรวจกับรายงานจริงแล้วพบว่ามีแค่ Task 4 เท่านั้น) ข้อสรุปที่ใช้ได้
   จริงคือ grep ตอนวางแผนควรครอบคลุม `WBWTests/` ด้วยเสมอ ไม่ใช่แค่โค้ดที่ใช้งานจริงใน `WBW/`

6. **เมฆกระตุก/ซ้อนตอนสลับแท็บกลับมาแผนที่ซ้ำ — ไม่ใช่ความเสี่ยงที่สเปกเปิดไว้ แต่เจอจริงและแก้แล้ว**
   ลูปสั่ง `playAnimation` ตัวแรกใน Task 6 (`b133bc6`) ไม่มี guard กันรันซ้ำตอน `RealityView`
   remount (สลับแท็บออกแล้วกลับมา) ขณะที่ `MapModelLoader.model()` คืน entity ตัวเดิมไม่ clone
   ทำให้ทุกรอบ remount สั่งแอนิเมชันทับซ้อนของเดิม แก้ในรอบต่อมา (`ec48e31`) ด้วยธง
   `hasStartedCloudAnimations` ที่รีเซ็ตตอน memory warning ด้วย — ยืนยันด้วย pixel diff ตัวเลขจริง
   (ดูแถว 7) ไม่ใช่แค่อ่านโค้ดแล้วเชื่อว่าใช้ได้

7. **เวลาโหลดโมเดลช้าลง ไม่ได้เร็วขึ้นตามที่สเปกทิ้งคำถามไว้เป็นความเสี่ยงเปิด** — สเปก §8 บอกว่า
   mesh มากกว่าเดิม 15% แต่ texture เล็กลงครึ่ง "ยังไม่รู้ว่าสุทธิแล้วดีขึ้นหรือแย่ลง" ของจริงที่วัดได้
   (แถว 8) คือ **แย่ลง** — 8.18 วิ เทียบ 7.5 วิ ของใบเก่า (~9% ช้ากว่า) แผนนี้ตัดสินใจแล้วว่า**ไม่แก้**
   ในรอบนี้ ปล่อยให้รอบถัดไปพิจารณาทางเลือก "รวม mesh ตาม material" ที่สเปกเตรียมไว้เป็นทางออก
