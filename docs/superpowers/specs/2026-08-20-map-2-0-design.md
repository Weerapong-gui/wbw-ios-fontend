## 3. พิกัด — anchor แทน bounds

### 3.1 ที่มาของตัวเลข

กรอบเดิม (`bounds` south 20.02371 / west 99.88272 / north 20.06727 / east 99.92288) มาจาก
Procrustes fit กับจุดสำรวจจริง 7 จุด และถูกแมปกับ bbox ของแผ่นเก่า ±2235.2954 × ±2580.8867
ถอดกลับเป็นสเกลของโมเดลได้:

```
unitsPerDegreeLongitude = (99.92288 − 99.88272) / 4470.5908 ผกผัน = 111,319.49
unitsPerDegreeLatitude  = (20.06727 − 20.02371) / 5161.7734 ผกผัน = 118,498.01
origin (0,0) ของโมเดล   = lat 20.04549, lng 99.90280   (bbox เก่าสมมาตรรอบศูนย์)
```

ตัวเลขคู่นี้คือ **EPSG:3857 (Web Mercator) เป๊ะทุกตำแหน่งทศนิยม**:
`6378137 × π/180 = 111,319.49` และ `111,319.49 / cos(20.04549°) = 118,498.01`
แปลว่าโมเดลจาก maps3d.io เป็นเมตร Web Mercator ไม่ใช่เมตรพื้นจริง (ต่างกัน 6.4% ที่ละติจูดนี้) —
อธิบายได้ว่าทำไมกรอบเก่าถึง "ใหญ่กว่าความจริง" อยู่ตลอดโดยที่ fit ยังผ่าน

ตรวจอิสระอีกชั้น: `marker_1` แปลงกลับได้ 20.04155 / 99.89656 เทียบ "วิหารพระเจ้าล้านทอง"
ในลิสต์ checkpoint ของ backend (20.04148 / 99.89658) — **ห่างกัน 8 เมตร**

พิกัดที่ถอดได้ทั้งชุด (ค่าคำนวณ ไม่ใช่ค่าสำรวจ — เอาไปตรวจกับคนจัดงานได้ แต่ยังไม่เอาไปแก้ backend):

| ฐาน | lat | lng | ฐาน | lat | lng |
|---|---|---|---|---|---|
| 1 | 20.04155 | 99.89656 | 5 | 20.04454 | 99.90955 |
| 2 | 20.03660 | 99.89930 | 6 | 20.05100 | 99.90932 |
| 3 | 20.03498 | 99.90004 | 7 | 20.05287 | 99.91135 |
| 4 | 20.03540 | 99.90474 | 8 | 20.05533 | 99.90914 |

ข้อจำกัดความแม่นยำเดิมยังอยู่: scatter ต่อจุดราว 110 ม. มาจากความหยาบของการปักหมุดในโมเดลเอง
ไม่ใช่ความคลาดของ GPS

### 3.2 ทำไมต้องเลิกใช้ bbox

โค้ดเดิมวางจุด GPS ด้วย `visualBounds` ของ **ทั้งโมเดล**:
`center + point × half` โดย `point` เป็นสัดส่วน −1…1 ที่ `Map3DGeo` คืนมา

ใบใหม่พังกฎนี้สองทาง:

1. **ความสูง** — เดิมจุดถูกวางที่ `center.z + half.z` ซึ่งคือยอดโมเดล ใบใหม่มีเมฆสูงถึง ~1160
   หน่วย จุดจะไปลอยเหนือเมฆ มองไม่เห็นบนแผนที่เลย
2. **แนวราบ** — แผ่นเก่าเป็นผืนผ้า ±2235 × ±2581 แผ่นใหม่เกือบจัตุรัส ±2292 × ±2288
   สัดส่วนคนละแบบ ใช้ `bounds` เดิมต่อ = จุดเพี้ยนทั้งแผนที่

โมเดลเป็นหน่วยเมตรจริง (`metersPerUnit = 1`) และเรารู้ origin กับสเกลแล้ว จึงคำนวณตำแหน่งเป็น
หน่วยโมเดลตรง ๆ ได้ ไม่ต้องพึ่ง bbox อีก — เมฆ ต้นไม้ หรืออะไรก็ตามที่ใส่เพิ่มมาในโมเดลรอบหน้า
จะไม่ขยับจุด GPS อีกเลย

### 3.3 สคีมา `map_config.json` ใหม่

(ย่อบางส่วนให้อ่านง่าย ไม่ใช่ JSON ที่ก็อปไปวางได้ตรง ๆ)

```json
{
  "modelName": "map",
  "framingYawDegrees": 90,
  "anchor": {
    "originLatitude": 20.04549,
    "originLongitude": 99.90280,
    "unitsPerDegreeLatitude": 118498.01,
    "unitsPerDegreeLongitude": 111319.49,
    "halfSpanUnitsEastWest": 2230.0,
    "halfSpanUnitsNorthSouth": 2230.0,
    "userDotHeightUnits": 320.0
  },
  "camera": { "…เท่าเดิมทุกค่า…" },
  "sky": { "domeRadius": 9.0 },
  "pins": [
    { "sequence": 1, "entityNames": ["marker_1", "markerNum_1"] },
    "… ถึง sequence 8 …"
  ]
}
```

- `bounds` หายไป แทนด้วย `anchor`
- `sky.apronSpanMultiplier` หายไปพร้อมม่านขอบ (§4)
- `pins[].entityName` (เดี่ยว) → `pins[].entityNames` (ลิสต์) เหตุผลใน §5
- `halfSpanUnits*` = 2230 คือขอบภูมิประเทศจริง (`tinMesh` extent) ไม่ใช่ขอบแผ่นไม้ 2292 —
  นอกกว่านั้นคือเนื้อตอไม้ ไม่ใช่พื้นที่งาน
- `userDotHeightUnits` = 320 สูงกว่ายอดภูมิประเทศ 306.57 เล็กน้อย และต่ำกว่าเมฆ (624+) มาก
- `Map3DConfig.fallback` ต้องตรงกับไฟล์นี้เป๊ะ (`Map3DConfigFileTests` คุมอยู่)

### 3.4 API ที่เปลี่ยน

```swift
extension Map3DGeo {
    /// พิกัดในหน่วยของโมเดล (x = ตะวันออก+, y = เหนือ+) · nil = อยู่นอกพื้นที่งาน
    static func modelUnits(latitude: Double, longitude: Double,
                           in anchor: Map3DConfig.Anchor) -> SIMD2<Float>?
}
```

```
x = (longitude − originLongitude) × unitsPerDegreeLongitude
y = (latitude  − originLatitude)  × unitsPerDegreeLatitude
nil เมื่อ |x| > halfSpanUnitsEastWest หรือ |y| > halfSpanUnitsNorthSouth
```

`Map3DGeo.modelPoint(latitude:longitude:in:)`, `Map3DGeo.Bounds` และ `Map3DGeo.eventArea`
**ถูกลบทิ้งทั้งสามตัว** — grep แล้วผู้เรียกเดียวคือ `Map3DScreen` บรรทัดที่กำลังเขียนใหม่อยู่นี้เอง
(กับเทสของมันเอง) เก็บไว้เป็นค่าคำนวณจาก anchor ก็ไม่มีใครใช้

ใน `Map3DScreen` โค้ดวางจุดยุบเหลือ:

```swift
dot.position = SIMD3<Float>(p.x, p.y, anchor.userDotHeightUnits)   // เครื่องหมาย y ดูข้อล่าง
```

ไม่มี `visualBounds` ไม่มีการหารด้วย `map.scale` สำหรับตำแหน่ง (ยังหารอยู่เฉพาะรัศมีลูกกลม)

**เครื่องหมายแกน Y ต้องพิสูจน์ด้วยตา ไม่ใช่ด้วยเหตุผล** โค้ดเดิมกลับเครื่องหมาย `point.y` ไว้
พร้อมคอมเมนต์ว่า `visualBounds(relativeTo: map)` ตอบแกน Y/Z สลับกับที่เห็นบนจอ และ
"สาเหตุที่แท้จริงไม่ทราบ" · รอบนี้มีของตรวจแล้ว: ป้อนพิกัด `marker_5` (20.04454, 99.90955)
เป็น GPS ปลอม จุดต้องทับหมุดที่มีเลข 5 ปั้นอยู่ ถ้าไปโผล่ฝั่งตรงข้ามคือเครื่องหมายกลับ (§7 ข้อ 4)

## 4. ท้องฟ้า เมฆ ขอบแผ่น

`Map3DSky.build(halfX:halfZ:slabDepth:)` → **`build()`** ไม่รับพารามิเตอร์

ตาย: `EdgeCurtain` (ม่านขอบ), `EdgeApron` (ชายพื้น), `apronPlacement`, `edgeCurtainImage`,
`apronName`, `sky.apronSpanMultiplier` และสองเทสใน `Map3DSkyTests` ที่จับ `apronPlacement`

อยู่ต่อ: โดมฟ้า (`domeRadius` จาก config) และชั้นเมฆ intro ที่ระยะ 2.9 / 2.2 / 1.6 หน่วย
ซึ่งถูกปิดทิ้งเมื่อ intro เล่นจบเหมือนเดิม

เหตุผลที่ตัดม่านได้: ม่านทั้งสองมีไว้ปิด "สันตัด" ของแผ่นเก่าที่เป็นหน้าตัดเปล่า ใบใหม่ `stumpBase`
เป็นตอไม้จริง ผิวข้างเป็นเปลือกไม้ หนา 150 หน่วยและปิดก้นในตัว ม่านกลายเป็นกระโปรงคลุมทับลายไม้

**ทางถอย ถ้าภาพไม่ผ่าน:** เงื่อนไขที่เคยทำให้ม่านเกิดคือมุมเงยต่ำสุด (34°) กับระยะไกลสุด (4.0)
ถ้าภาพที่มุมนั้นเห็นก้นแผ่นหรือเห็นฟ้าลอดใต้ขอบ ให้เอา apron กลับมาตัวเดียว โดยคำนวณความกว้าง
จาก `halfSpanUnits*` ไม่ใช่จาก bbox แล้วบันทึกเหตุผลไว้ในสเปกนี้

**เมฆในโมเดล — เล่นวนตลอด:** หลัง `root.addChild(map)` ไล่ทั้งต้น entity เก็บ
`availableAnimations` แล้ว `playAnimation(.repeat())` ทุกคลิป · ต้องไล่ทั้งต้นเพราะ Blender ยัด
`timeSamples` ไว้ที่ `cloud_*` แต่ละก้อน ไม่ใช่คลิปเดียวที่ราก · โค้ดส่วนนี้อยู่หลัง
`Map3DScreen.shouldRender` guard อยู่แล้ว เทสจึงไม่แตะ

เมฆโมเดล (0.27–0.50 หน่วยหลังย่อสเกล) กับเมฆ intro ของแอป (1.6–2.9) อยู่คนละชั้น ไม่ทับกัน

## 5. หมุดกับการแตะ

`Pin` รับชื่อได้หลายชื่อต่อฐาน เพราะเลข `markerNum_N` เป็น **พี่น้อง** ของ `marker_N` ใต้ `root`
ไม่ใช่ลูก · โค้ดแตะปัจจุบันไต่ขึ้นหาพ่อจนเจอชื่อในตาราง ไต่จาก `markerNum_5_mesh` จะไปโผล่ `root`
แล้วเงียบ — คนแตะเลขที่เห็นชัดที่สุดบนจอแล้วไม่มีอะไรเกิดขึ้น

- `Map3DPins.entityNames` → ชื่อทั้งหมดทุกฐานรวมกัน (ใช้ตอนติด collision)
- `Map3DPins.sequence(forEntityNamed:)` → หาในลิสต์รวม
- `Map3DPins.primaryEntityName(for:)` → ชื่อแรกของฐานนั้น (`marker_N`) ให้กล้องโฟกัสไปที่ตัวแท่ง
  ไม่ใช่ตัวเลขที่ลอยสูงกว่า
- `Map3DScreen` ติด `CollisionComponent` + `InputTargetComponent` ให้ทุกชื่อ (วนอยู่แล้ว
  เปลี่ยนแค่แหล่งลิสต์) และตอนแตะติดให้ `focus(on:at:)` ใช้ตำแหน่งของ primary entity

`Map3DPins.label(sequence:checkedIn:)` ไม่เปลี่ยน — ชื่อฐานยังมาจาก `CheckinProgressStore`
เหมือนเดิม ฐานที่ยังไม่เช็คอินยังขึ้น "ฐานที่ N" ห้ามเดาชื่อ

## 7. ยืนยันด้วยของจริง (ไม่ยืนยัน = ยังไม่เสร็จ)

1. `xcodebuild -scheme WBW -configuration Debug -destination 'platform=iOS Simulator,name=iPhone 17' build` ผ่าน
2. `… test` ผ่านทั้งชุด
3. สกรีนช็อตจาก simulator: แผนที่ขึ้นครบ เห็นตอไม้ ต้นไม้ และเลขบนหมุด
4. `-uitestMapPin 5` → การ์ดขึ้น "ฐานที่ 5" และกล้องบินไปหมุดที่มีเลข 5 ปั้นอยู่จริง
5. GPS ปลอม `20.04454, 99.90955` → จุดฟ้าทับหมุดเลข 5 (ตัวตัดสินเครื่องหมายแกน Y §3.4)
6. `-uitestMapPitch 34` + ระยะไกลสุด → ไม่เห็นก้นแผ่น ไม่เห็นฟ้าลอดใต้ขอบ (ตัวตัดสินเรื่องม่าน §4)
7. เมฆขยับจริง — ถ่ายสองเฟรมห่างกันแล้วเทียบ
8. อ่านเวลาโหลดจาก `NSLog` เทียบ 7.5 วิของใบเก่า บันทึกตัวเลขไว้ ไม่แก้ในรอบนี้

## 8. ความเสี่ยงที่ยังเปิดอยู่

- **RealityKit อาจไม่แปลง `timeSamples` ของ Blender เป็น `availableAnimations`** — ถ้าไม่มีคลิป
  โผล่มา เมฆก็ค้างนิ่ง แผนที่ยังใช้ได้ทุกอย่าง ไม่บล็อกงาน บันทึกเป็นข้อจำกัดแทนการเขียน
  แอนิเมชันเอง
- **เวลาโหลด** — mesh มากกว่าเดิม 15% แต่ texture เล็กลงครึ่ง ยังไม่รู้ว่าสุทธิแล้วดีขึ้นหรือแย่ลง
  ถ้าแย่ลงชัดเจน เปิดรอบใหม่ทำ "รวม mesh ตาม material" ใน Blender (ทางเลือก C ที่ตัดออกจาก §1)
- **พิกัดฐานที่ถอดได้ใน §3.1 ยังไม่ผ่านการสำรวจ** — แมปพิกัดทั้งสี่แถวที่มีในลิสต์ backend
  เข้าหน่วยโมเดลผ่าน anchor ชุดที่ ship จริงแล้วเทียบกับหมุดที่ใกล้ที่สุด ได้ผลว่า **ตรงแค่ 1 จาก 4**
  ไม่ใช่ "มี `marker_2` ตัวเดียวที่เพี้ยน" อย่างที่ร่างแรกของข้อนี้เข้าใจ:

  | แถวใน seed | หน่วยโมเดล | หมุดใกล้สุด | ระยะ |
  |---|---|---|---|
  | id 1 วิหารพระเจ้าล้านทอง (20.04148, 99.89658) | (−692, −475) | `marker_1` | ~9 |
  | id 2 สวนกุหลาบ (20.04390, 99.89900) | (−423, −188) | `marker_1` | ~389 |
  | id 5 จุดปลูก (20.05300, 99.90080) | (−223, 890) | `marker_8` | ~969 |
  | id 8 ฐาน Zero Waste (20.05120, 99.89290) | (−1102, 677) | `marker_1` | ~1214 |

  สามแถวล่างไม่ได้ "อยู่ใกล้หมุดผิดตัว" แต่ไม่มีหมุดไหนใกล้เลย · **แต่ลิสต์ชุดนั้นเป็นข้อมูล seed
  ใน unit test ของ Go ที่ถูกยกมาไว้ในเอกสารแผน `docs/superpowers/plans/2026-08-06-sos.md`
  ไม่ใช่ตาราง checkpoint จริงของ backend** อ่านตรงไปตรงมาที่สุดคือคนเขียนเทสนั้นหาพิกัดจริงมาแถวเดียว
  แล้วกรอกที่เหลือเอง ซึ่งทำให้มันเป็นหลักฐานที่อ่อน ไม่ใช่หลักฐานหนักแน่นว่าแมปผิด — และมันตัดสิน
  ไม่ได้ทั้งสองทาง · งานที่ต้องทำจริงคือเทียบทั้งแปดแถวกับตาราง checkpoint จริง เปิดค้างไว้เป็นงาน
  ก่อนวันงานที่ `docs/map-2-0-verification.md` (ส่วน "ข้อที่ยังเปิดอยู่")
