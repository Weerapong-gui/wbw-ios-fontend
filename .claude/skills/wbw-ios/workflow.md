## เทส

**XCTest ล้วน 22/22 ไฟล์ ใน `WBWTests/`** (`import Testing` ของ Swift Testing มี 0 ไฟล์ตอนนี้) —
**จะเอา Swift Testing เข้ามาต้องคุยก่อน** อย่าเผลอใช้เพราะเห็นเป็นของใหม่กว่า ตั้งชื่อไฟล์
`<Thing>Tests.swift` วางแบนที่รากของ `WBWTests/` ไม่มีโฟลเดอร์ย่อย

assert ควรมีข้อความไทยบอกเหตุผลว่าทำไมค่านั้นสำคัญ ไม่ใช่แค่ assert เฉย ๆ ตัวอย่างจริง
(`WBWTests/Map3DCameraTests.swift`):

```swift
XCTAssertGreaterThan(Map3DCamera.minPitch, 0, "มุมต่ำสุดต้องอยู่เหนือเส้นขอบฟ้า")
```

logic ที่อยากเทส ให้แยกเป็น `static func` บริสุทธิ์ (รับค่าเข้า คืนค่าออก ไม่มี state ของ View ติดมา)
แทนที่จะฝังไว้ในตัว View แล้วเทสไม่ถึง ตัวอย่างจริง: `Map3DCamera.clampPitch`
(`WBW/Map3D/Map3DCamera.swift`) และ `ForestSceneHost.shouldClaim`
(`WBW/Scene3D/ForestSceneHost.swift`) — เทสเรียกฟังก์ชันตรง ๆ ได้เลยโดยไม่ต้อง mount View ทั้งจอ

## commit

conventional prefix (`feat`/`fix`/`docs`/`refactor`) ตามด้วยสรุปเป็นภาษาไทย ของจริงจาก `git log`:

```
fix(map): หันทิศโมเดลรอบแกนตั้งของตัวเอง ไม่ใช่แกน Y ของโลก
refactor(map): ถอด MapLibre ออกจากโปรเจกต์
```

**`git add` ทีละไฟล์เสมอ ห้าม `git add -A` / `git add .`** — repo นี้มักมีงานอื่นที่ยังไม่ commit วางอยู่
ข้าง ๆ (เช่นตอนเขียนไฟล์นี้มีโฟลเดอร์ `claude-code-server-side-swift-skills/` ที่ยัง untracked) ใช้
`-A`/`.` แล้วจะดึงเข้ามาด้วยโดยไม่ตั้งใจ ตรวจ `git status` ก่อน commit ทุกครั้งเพื่อดูว่าไฟล์ที่กำลังจะ
`add` ตรงกับที่ตั้งใจจริงไหม โดยเฉพาะ **`Config.backend` ที่สลับไว้ทดสอบต้องไม่ติดไปด้วย** (รายละเอียดดู
`.claude/skills/wbw-ios/backend-and-config.md`)

คำสั่งที่ใช้อยู่ที่ `.claude/skills/wbw-ios/build-and-run.md` (ไม่ซ้ำคำสั่งไว้ที่นี่ กันสองไฟล์เขียนคน
ละคำสั่งแล้วไม่ตรงกัน) งานที่แตะ UI ต้องมีสกรีนช็อตจาก simulator ประกอบด้วยเสมอ (วิธีเก็บอยู่ในไฟล์
เดียวกัน) — ห้ามเคลมว่าจอ "น่าจะออกมาถูก" จากการอ่านโค้ดอย่างเดียวโดยไม่เห็นภาพจริง

## skill เน่าเมื่อไหร่

ไฟล์ทั้ง 5 ใบใน `.claude/skills/wbw-ios/` (`SKILL.md`, ไฟล์นี้, `backend-and-config.md`,
`build-and-run.md`, `ui-conventions.md`) อธิบายสภาพ repo ณ วันที่เขียน ไม่ใช่กติกาที่ตายตัวตลอดไป —
`SKILL.md` คือไฟล์เดียวที่การันตีว่า session ถัดไปจะอ่านก่อนเสมอ (`CLAUDE.md` ชี้มาที่ไฟล์นั้นตรง ๆ)
แล้วเชื่อทันทีโดยไม่ตรวจซ้ำ ถ้างานไหนทำให้ข้อความในไฟล์เหล่านี้ผิดไปจากความจริง เช่น ย้าย/เปลี่ยนชื่อไฟล์
ที่ถูกอ้าง path ไว้ตรง ๆ, เปลี่ยนคำสั่ง build/test, เพิ่มหรือลบ `case` ใน `enum Backend`, จำนวนไฟล์เทส
XCTest ไม่ใช่ 20 อีกต่อไป, หรือแก้ไฟล์ที่ถูกอ้างเลขบรรทัดตรง ๆ จนเลขนั้นขยับ (เช่น `ui-conventions.md` อ้าง
`WBW/Config.swift:66` และ `WBW/HomeView.swift:108` — แทรกโค้ดไว้เหนือบรรทัดพวกนั้นแล้วเลขจะเพี้ยนแบบเงียบ ๆ
ไม่มี build/test ตัวไหนจับได้) — **ให้แก้ไฟล์ skill ที่เกี่ยวข้องในคอมมิตเดียวกับงานที่ทำให้มันเปลี่ยน
ไม่ปล่อยไว้ทีหลัง** เพราะถ้าปล่อยไว้ ไฟล์นี้จะกลายเป็นตัวพา session ถัดไปตัดสินใจผิดตั้งแต่ต้น (เช่น สั่ง
รันคำสั่ง build ที่ใช้ไม่ได้แล้ว หรือเชื่อว่ามี `Backend` case ที่ถูกลบไปแล้วจริง ๆ)

`./scripts/check-skill-refs.sh` จับส่วนที่จับด้วยเครื่องได้: จำนวนไฟล์ที่ skill การันตีไว้ (36 ที่ราก
`WBW/`, 20 เทส, `import Testing` = 0 ฯลฯ), path ทุกอันที่ skill อ้างว่ายังมีอยู่จริง, และเลขบรรทัดแบบ
`path:NN` ว่าไม่เกินท้ายไฟล์ พร้อมพิมพ์บรรทัดปัจจุบันออกมาให้อ่านเทียบเองว่ายังชี้ของถูก (เนื้อหาบรรทัดตรง
กับที่ skill เล่าไหม เครื่องตัดสินแทนไม่ได้ ต้องใช้ตา) — รันก่อน commit งานที่ย้าย/เพิ่ม/ลบไฟล์ ตัวเลขที่
สคริปต์เช็คถูก hardcode ไว้ในนั้น แก้พร้อมกับแก้ข้อความใน skill เสมอ ห้ามแก้ให้ผ่าน ๆ อย่างเดียว
